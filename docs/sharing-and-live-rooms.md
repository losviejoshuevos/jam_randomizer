# Sharing и живые комнаты

## Что хранится где

Музыкальная сессия сжимается `fflate`, кодируется в base64url и помещается в параметр `jam` переносимой ссылки. В живой комнате тот же payload временно хранится в Redis, чтобы передать подключённым музыкантам следующий джем без нового QR. Переносимая ссылка остаётся рабочей независимо от localStorage, комнаты и срока её жизни.

Экспортируемый `.jam.json` содержит ту же `JamSession` в читаемом виде. При импорте структура проверяется до изменения текущей карточки.

LocalStorage хранит текущую сессию, черновые настройки, до 30 последних сессий и отдельное избранное.

## Временная комната

Комната содержит только:

- случайный `roomId`;
- хеш секрета ведущего;
- идентификатор и переносимый payload сессии;
- индекс текущего шага формы;
- статус `idle`, `playing`, `paused`, `complete`, `waiting` или `terminated`;
- оставшееся время, ревизию и время обновления;
- срок истечения.

При создании комнаты ведущий получает секретный token. Он хранится только в состоянии ведущего и `sessionStorage`; в QR и гостевую ссылку token не попадает. Изменять комнату может только запрос с этим token.

По умолчанию TTL равен 7 200 секундам — двум часам после последнего heartbeat ведущего. Полная сессия в ссылке продолжает работать и после истечения комнаты, но без живой синхронизации.

## Локальная проверка без Redis

1. Запустить `npm run dev`.
2. Открыть редактор по `http://localhost:3000` и создать сессию.
3. Перейти в Stage Mode и нажать «Подключить экраны».
4. На втором окне открыть тестовую ссылку или отсканировать QR телефоном.
5. Для телефона использовать адрес `Network`, напечатанный Next.js, например `http://192.168.1.35:3000`.
6. Оба устройства должны быть в одной Wi-Fi сети; macOS Firewall должен разрешать входящие соединения Node.js.

Локальный adapter хранит комнаты в памяти процесса. После перезапуска dev-сервера комнаты исчезают — это ожидаемо.

## Синхронизация и диагностика

При старте живой комнаты ведущий назначает первую долю примерно на 1,5 секунды вперёд по серверному времени. Ведомый экран измеряет смещение своих часов относительно сервера и восстанавливает текущую долю по общей временной отметке, даже если SSE-событие пришло с задержкой. Звуковой метроном остаётся только у ведущего, режим светового метронома каждый ведомый экран выбирает локально.

Для диагностики добавьте `debug=1` к гостевой ссылке. Например, если ссылка уже содержит параметры, добавьте `&debug=1`. На ведомом экране появится блок с состоянием SSE, сетевой задержкой и кнопкой «Скопировать диагностику»; те же обновления комнаты выводятся в консоль браузера.

После завершения ведущий может закрыть комнату или оставить музыкантов подключёнными. Во втором случае редактор сохраняет capability комнаты в `sessionStorage`, поддерживает heartbeat и передаёт новую сессию при следующем открытии Stage Mode.

Изменения комнаты доставляются SSE-функции через Redis Pub/Sub. При обновлении состояния ведущий одной pipeline-командой сохраняет актуальный снимок комнаты и публикует событие. Поэтому каждое подключённое ведомое устройство больше не выполняет отдельное чтение Redis раз в секунду. Периодическая проверка живости ведущего выполняется внутри уже запущенной SSE-функции по последнему полученному состоянию.

Если heartbeat ведущего отсутствует 15 секунд, ведомые замораживают сессию и ждут восстановления связи до пяти минут. Затем комната удаляется. Фаза `terminated` немедленно закрывает SSE и хранится не более минуты, чтобы событие успело дойти до клиентов.

## Production на Vercel и Upstash

1. Создать Upstash Redis через Vercel Marketplace или Upstash Console.
2. Добавить в Vercel Project Settings → Environment Variables:
   - `UPSTASH_REDIS_REST_URL`;
   - `UPSTASH_REDIS_REST_TOKEN`;
   - опционально `JAM_ROOM_TTL_SECONDS=7200`;
   - аварийный рубильник: `LIVE_ROOMS_ENABLED=false` и `NEXT_PUBLIC_LIVE_ROOMS_ENABLED=false`.
3. Допускаются автоматически созданные Vercel KV имена `KV_REST_API_URL` и `KV_REST_API_TOKEN`.
4. Выполнить redeploy.

SSE-функция держит соединение до 285 секунд, затем браузерный `EventSource` автоматически подключается заново. При каждом подключении первой отправляется последняя ревизия комнаты, поэтому пропущенное событие не оставляет экран в старом состоянии.

## Границы первой версии

- Ведомый экран не воспроизводит звук метронома и не управляет сессией.
- Между действием ведущего и карточкой гостя остаётся небольшая сетевая задержка доставки события; метроном и таймер восстанавливают фазу по общей серверной временной отметке.
- Синхронизируются старт, пауза, продолжение, сброс, фактический переход после квадрата, автоматический переход, завершение и повторный запуск.
- Ссылка может стать слишком большой для QR при экстремально большой будущей модели сессии; копирование ссылки и файл при этом остаются доступны.
